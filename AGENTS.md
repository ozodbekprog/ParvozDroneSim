- Исходная точка следующих итераций — текущий работающий интерфейс публичной
  версии целиком: его структура, логика, компоновка и состояния. Одного фона

  изменение допустимо как последовательность проверенных пользователем шагов.

  на Git commit/push не заменяют разрешение на обновление публичного UI.
- При выпуске иных исправлений не включать попутно неразрешённые изменения UI.
  Текущую публичную версию интерфейса сохранять до разрешённого выпуска.

## Локальная приёмка и продолжение после лимита

- Для задач диагностики и справочника использовать существующий пилот
  `tools/acceptance/README.md`: отдельные исходники/сборка/база, машинные проверки,
  затем реальные доказательства Chrome. Для иных задач выбирать соответствующие
  проверки; этот пилот не подтверждает весь продукт или FPS целевого ноутбука.
- Если задача прервалась, сначала прочитать `data/acceptance/latest.json`, затем
  checkpoint/CONTINUE.md нужного запуска и проверить его threadId/цель.
  Продолжать этот запуск через `npm run acceptance -- resume --run ID --serve`,
  сохраняя уже пройденные этапы. Изменённые исходники требуют нового снимка.
- После смены аккаунта читать свежие оба окна лимита и заново проверять Chrome.
  После мягкого восстановления идентификатор браузерного соединения может
  измениться: обнаружить то же расширение/профиль и повторно привязать вкладку.
  Перезапуск native host сам по себе не доказывает доступ. Порядок — в
  `tools/acceptance/BROWSER-SCENARIO.md`. Не автоматизировать вход/Stop/Continue
  в окне Codex; использовать сохранённое состояние и штатные инструменты.

## GitHub: обязательное сохранение изменений

- Согласованный приватный репозиторий: https://github.com/Fayzullo637/ParvozDroneSim ; `origin` — `https://github.com/Fayzullo637/ParvozDroneSim.git`, основная ветка `main`. Название продукта: **Parvoz Drone Simulator**, кратко **Parvoz Drone Sim**, словесный знак **PARVOZ**. Рабочую папку и внутренние ключи сохранений не переименовывать ради ребрендинга.

- По явному запросу пользователя GitHub служит постоянной историей проекта для отката и продолжения на другом компьютере. После каждого небольшого, законченного и проверенного изменения создавать отдельный понятный commit и выполнять обычный push в согласованный `origin`. Эта инструкция разрешает такие последующие commit/push без повторного запроса подтверждения.
- В начале работы проверять `git status`, текущую ветку и `git remote -v`; учитывать незакоммиченные изменения пользователя и других чатов. Не объединять чужие незавершённые изменения со своим commit. Перед новой работой проверять удалённую историю; при чистом рабочем дереве обновляться через `git pull --ff-only`. Не затирать чужие изменения, не использовать force push, `reset --hard` или `clean -fd`.
- Коммитить код, документы, канонический `content/`, редактируемые `.blend` и происхождение/лицензии ресурсов. Крупные двоичные файлы хранить через Git LFS по `.gitattributes`. Сохранять проверенный ZIP Ironworks для ручного восстановления; автоматически карту не возвращать.
- Не коммитить секреты, env, SSH-ключи, базы игроков, `node_modules`, сборки, временные файлы, кэши импорта и повторные архивы выпусков. Соблюдать `.gitignore`; перед commit проверить состав изменений и отсутствие секретов. Инструкция по работе и восстановлению: `docs/GITHUB-WORKFLOW.md`.
- Репозиторий с импортированным Liftoff-контентом должен оставаться приватным: разрешение пользователя на онлайн-тест не является подтверждением лицензии на распространение. Не включать платные услуги GitHub/LFS и не менять видимость репозитория автоматически.
- В конце каждого чата сообщать ветку, commit и результат push. Успех подтверждать совпадением локального и удалённого SHA. Если доступ/сеть/лимит мешает push, сохранить локальный commit и явно сообщить, что GitHub ещё не обновлён. Push на GitHub и выпуск на Oracle — отдельные действия.

## Качество 3D-контента

- Финальные модели создавать и редактировать средствами Blender либо использовать полноценные модели с подходящей лицензией.
- Генерация наборов коробок, цилиндров и других примитивов допустима только для временного макета и невидимых коллизий. Такой результат нельзя выдавать за готовую детализированную графику.
- Скрипты использовать для подготовки, импорта, оптимизации, запекания, проверки и экспорта. Массовая расстановка примитивов не заменяет художественное моделирование.
- Обязательны проработанный силуэт, корректные пропорции, скругления, UV-развёртка и материалы. Круглые детали должны выглядеть круглыми на предполагаемой дистанции просмотра.
- Сохранять редактируемые `.blend`-исходники. Проверять результат крупным планом, с нескольких сторон и непосредственно в игре на Low.
- Детализацию оценивать по видимому результату, а не по числу объектов, полигонов или факту использования Blender.
- Для сторонних ассетов сохранять автора, исходную ссылку и лицензию. Для собственного выпуска использовать собственные или бесплатные ассеты; платные покупки не согласованы. По последующему явному запросу пользователя разрешён локальный импорт установленных карт и дронов Liftoff для проверки. Право распространения не подтверждено: такой контент исключать из публичного выпуска.

## Цель производительности

- Минимальный ориентир: Intel i5 со встроенной UHD 620, Low, настоящее внутреннее разрешение 1280×720.
- Цель: 60 FPS, медиана времени кадра ≤16,7 мс, 1% low ≥50 FPS. Проверять на целевом ноутбуке; замер на другой машине не является подтверждением.
- Во время приёмочного замера отключать адаптивное разрешение. Записывать реальный размер framebuffer, backend, время кадров, треугольники и draw calls.
- Предварительные бюджеты Low: 150–300 тысяч видимых треугольников, до 250 draw calls, до 256 MiB текстур с mip-уровнями. Это ограничения производства, а не гарантия FPS.
- Существующие параметры полёта и ID Kestrel сохранять. Новую карту выпускать как `ironworks-v2` с отдельной трассой и заданием.

## Проверка FPS и фризов: обязательный реальный полёт — 2026-11-01

- Пользователь наблюдает фризы при быстром полёте по траекториям, поворотах и
  смене направлений. Проверять этот сценарий в движении: разгон, пролёты по
  разным участкам карты, манёвры и смена видимых объектов. Стоящий на земле
  или неподвижно зависший дрон этот сценарий не воспроизводит.
- Перед записью и на всём измеряемом участке подтвердить, что дрон действительно
  летит: меняются его положение, скорость и направление. Сохранить маршрут и
  доказательства движения — видео либо последовательность наблюдений/кадров
  вместе с показаниями скорости/положения. Отправленные клавиши, открытый HUD,
  таймер полёта и число `gameplaySummary.frames` сами по себе этого не доказывают.
- Не заменять активный полёт кратким нажатием газа с последующим простоем.
  Для сравнения до/после повторять тот же маршрут, длительность и условия;
  первый и повторный проходы записывать отдельно.
- Неподвижная запись допустима только как явно названная проверка кнопок,
  экспорта или неподвижной сцены. Она не подтверждает игровой FPS, отсутствие
  фризов, их причину, прирост производительности или приёмку UHD 620.
- Если реальный полёт не удалось выполнить или подтвердить, записать
  «проверка производительности в полёте не выполнена» и остановить этот замер.
  Не продолжать собирать неподвижные логи как доказательство исправления.
  Порядок: `docs/STUTTER-PROFILING-20261026.md`.
