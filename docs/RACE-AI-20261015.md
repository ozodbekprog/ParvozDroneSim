# Physical opponents in solo Race — 2026-10-15

Ordinary solo Race now has three opponents (Aziza, Timur and Lola). Time Trial,
training, career, freestyle, tutorials and challenges retain their existing solo
rosters. Each opponent uses the player's selected physical build and existing
model assets. The pilots have different cruise speeds and launch reaction times.

`shared/race-ai.js` produces bounded throttle, pitch, roll and yaw sticks and
submits them through `simulateCommand` at the same 60 Hz fixed timestep as the
player. Angle assistance uses the existing controller. Motor dynamics, inertia,
gravity, drag, battery, health and authored map/race contacts remain physical.
There is no drone-to-drone collision: opponents and player can overlap without
applying forces to each other. Their progress is awarded only by `gateCrossed`
in the required order, with ordinary laps and finish times. Crashes and an
eight-second navigation stall use the player's `resetAtCheckpoint` rule; a reset
does not award a gate or rewind elapsed race time. After finishing, pilots fly to
their exit waypoint and physically hover while the player is still racing.

`shared/race-ai-navigation.js` checks swept spheres against the same imported
collision files as flight. The radius reserves the aircraft's full compound
collision extent. Legal gate apertures are sampled when their centre is occupied
by authored geometry. Obstructed links use a bounded 3D A* search (6,000 coarse
and 9,000 fine expansions per candidate), then shorten only collision-clear
segments. All opponents share the prepared routes and collider caches. Vertical
and horizontal velocity follow the same 3D segment, including raised Arena
platform approaches and Hangar detours.

## Client integration

Construct `SoloSession` after `world.load`, which has loaded and validated the
map and selected race collision JSON. During the loading screen, before starting
countdown, call:

```js
await solo.prepareOpponents(async () => {
  session.check();
  await nextPaint();
  session.check();
});
```

Preparation yields between gates and is shared by all three pilots. Normal race
updates join these cached routes with bounded segment checks; they do not run A*.
`solo.restart()` resets opponents and preserves the prepared geometry. Pause and
countdown freeze all pilots. The player's manual reset does not reset rivals.
The race continues after an opponent finishes and ends when the player finishes,
matching the existing solo results flow.

`solo.room.players` contains player and opponents. Preload/upsert every roster
entry, reset each visual when its own `resetId` changes, and record the entire
roster in replay frames. Only the player's reset should release user input.
All pilots share `solo.spec`; there are no new model downloads. `solo.item`,
`solo.state` and player checkpoint callbacks keep their existing meaning.

## Verification and limits

Run `node --test --test-isolation=none test/race-ai.test.js test/solo-session.test.js`.
The original 26 focused AI checks and eight existing SoloSession checks passed
locally on 2026-10-16. A subsequent 27th check passed all three skill profiles
together through the actual narrow practice course, with different finish times
and zero resets; the lifecycle check was rerun after the start-delay refinement.
The full 26-test run took 288.4 seconds while other local work was running; this
is a correctness run, not a target-hardware performance measurement.
The focused tests use the actual hashed collision JSON under `public/content/`
for every imported map and all 17 selectable tracks. They check one complete
physical lap per track, all authored laps on representative Hangar, Arena and
Minus Two courses, imported Gecko/Luma builds through narrow gates, ordered
physical gate crossings, bounded per-tick displacement, checkpoint recovery,
pause/restart isolation, and absence of aircraft-to-aircraft pushing. The
baseline Kestrel lap checks require zero resets and verify that no A* runs during
the race after preparation. The remaining stock drone builds and all possible
part combinations have not been exhaustively flown.

These checks verify physical navigation and lifecycle behavior. Visual race
acceptance and the UHD 620 frame budget require their own browser/hardware
measurements. Integration was published and finalized in
**20261016-hangar-race-01**, source **f51e38d**, on 16 October; actual public
browser verified the three-opponent Race HUD/startup. Canonical suite includes
