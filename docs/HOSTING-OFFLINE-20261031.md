# Перенос хостинга и полный офлайн — 31 октября 2026

Статус: исследование и рекомендуемая архитектура. Ни миграция, ни PWA ещё не
реализованы; публичная игра, DNS, облачные ресурсы и данные игроков не изменены.

## Условия пользователя

- Во время показа браузер нового устройства не открыл даже сайт. Точная ошибка,
  время и сеть неизвестны; причину того события пока нельзя установить.
- Полностью уйти с Oracle: клиент, ресурсы, аккаунты и мультиплеер.
- Основной сценарий показа: открыть URL на новом устройстве с интернетом.
- После скачивания должен работать весь одиночный контент без интернета.
- Аудитория: Узбекистан и СНГ. Только бесплатные квоты и имеющиеся кредиты Azure;
  расходов своими деньгами и автоматического перехода на pay-as-you-go нет.
- Действующий публичный UI — основа. Новые офлайн-кнопки/состояния сначала
  показываются отдельно; выпуск требует явного разрешения на показанный результат.

## Сравнение вариантов

| Вариант | Применение | Существенные ограничения |

| Cloudflare Static Assets/Pages + R2 + сервер в Azure | Альтернатива для более дешёвой раздачи карт и независимого размещения клиента | Pages: до 25 MiB на файл. R2 Standard: 10 GB-month, 1 млн A и 10 млн B операций бесплатно, без платы за исходящий трафик; сверх квот платно. Подключение R2 — тарифицируемая подписка, а не гарантированный жёсткий лимит $0. В основной вариант без отдельного решения не включать. |
| GitHub Student | Приватная история, сборки, доступные льготы на домен/облачные сервисы | Наличие Student не создаёт постоянно работающую игровую VM. Pages ограничен 1 GB сайта и мягким лимитом 100 GB/месяц, не запускает текущий Node/WebSocket-сервер; полный контент туда не помещается. |
| Google Drive | Архивы, резервные копии и ручная передача | Для загрузки ресурсов внутри игры предпочтительнее Blob/R2: управляемые HTTP/CORS/Range/cache-заголовки. Drive API имеет квоты и ответы 403/429; не закладывать его как основной CDN. |

### Кредиты — не бессрочный бесплатный сервер

Записанная Oracle-конфигурация: A1, 2 OCPU / 12 GB RAM. Бесплатный Azure
`B2ats_v2` имеет 2 vCPU, но всего **1 GiB RAM**; считать его улучшением нельзя.
Для текущего сервера сначала измерить память и длительную CPU-нагрузку на
изолированной базе. На burstable VM проверять поведение при исчерпании CPU credits.

Прямой GET официального Azure Retail Prices API 31 октября дал для Linux
`Standard_B2s`, Consumption, без Spot/Low Priority/Windows:

| Регион | USD/час | Только compute за 730 часов |
| --- | ---: | ---: |
| West Europe | 0.048 | 35.04 |
| UAE North | 0.0499 | 36.43 |

Это ориентир, не выбранный SKU и не полная смета. При таких ставках $100 —
менее трёх месяцев compute без бесплатного зачёта, дисков, IP и других услуг.
Фактические остаток, срок, бесплатные квоты, регионы и SKU подписки не проверены;
Azure CLI на этом компьютере не найден. Объявлять круглогодичную бесплатную
работу всего сервера оснований нет. Полный уход с Oracle возможен как ограниченная
по кредитам бета; бессрочная вместимость 20 игроков на $0 не подтверждена.

У Azure исходящий интернет-трафик сверх общей бесплатной квоты 100 GB/месяц
оплачивается по региону и маршруту. Массовая установка всего контента должна
учитываться отдельно от трафика небольшого клиента. Azure Students после
исчерпания кредита требует продления по условиям предложения либо перехода
на оплату. Сохранять spending limit, не включать платные сторонние Marketplace
услуги; бюджетные уведомления сами по себе **не останавливают расход**.

## Предлагаемое устройство игры

1. **Клиент независимо от API.** В SWA публиковать только проверенный клиент и
   малые статические зависимости. Использовать встроенный каталог той же версии;
   меню/локальный пилот/одиночный полёт не ждут `/catalog`, `/guest` или `/me`.
   Сетевые сервисы подключаются отдельно. На новом устройстве нужен интернет,
   но скачивание всего офлайн-пакета не должно задерживать первый вход.
2. **Ресурсы отдельно.** Blob Standard Hot LRS, версионированные неизменяемые
   файлы с существующими хешами; без обязательного Front Door/CDN на первом этапе.
   Разделить API, WebSocket и asset origins в публичной конфигурации клиента;
   секретов в ней нет. CORS только для разрешённых игровых адресов, GET/HEAD,
   нужных Range/If-Range и наблюдаемых заголовков. Не передавать токен аккаунта
   в хранилище ресурсов. Сохранить логические пути/ключи локального кэша.
3. **Полный PWA-офлайн.** Использовать `vite-plugin-pwa`/Workbox `injectManifest`
   для малого ядра, существующий менеджер загрузок — для больших ресурсов.
   Полный пакет скачивается явно, проверяется по фактическим файлам и хешам.
   Дозагрузка/повтор не стирают готовое; повреждение, нехватка квоты и удаление
   браузером возвращают честный статус неполной готовности. Запрашивать persistent
   storage и учитывать квоту; установка значка сама по себе ничего не доказывает.
4. **Версии без смешивания.** Клиент, каталог и офлайн-зависимости фиксируются
   одной версией; новую активировать после полной проверки, вне полёта. При
   недостатке места сохранить рабочую старую версию. Нынешний лимит retained
   2 GiB нельзя считать достаточным для одновременного хранения двух полных
   выпусков. API/auth/POST-ответы через Service Worker не подменять и не кэшировать.
5. **Локальные данные.** Без сети доступны свободный полёт, локальные гонки,
   испытания, уроки, карьера, ангар/настройки и локальные реплеи. Прогресс и
   сборки принадлежат отдельному локальному профилю; облачный аккаунт не
   перезаписывается. Рейтинг, серверные рекорды, вход, актуальный Weekly и
   мультиплеер требуют сервера. Офлайн-результаты не отправляются как заверенные
   сервером; практику Weekly не выдавать за официальное прохождение.
6. **Backend.** Сохранить Node 24, авторитетную симуляцию, текущий протокол и
   SQLite на постоянном диске одной Azure VM; без миграции на новую СУБД только
   ради переезда. Первоначальный предел — 20, переносится только после проверки
   соответствующей нагрузки. Резервные копии вынести в отдельный приватный Blob
   container с проверенным восстановлением. Не делать сразу два записывающих
   сервера из одной SQLite-копии.

Офлайн на новом никогда не посещённом устройстве без скачанных файлов невозможен.
На подготовленном — повторный запуск по тому же адресу или значку PWA. При смене
origin кэш, настройки и локальные реплеи не переносятся автоматически: использовать
экспорт/импорт, отдельные отчёты Start/Class и повторную загрузку ресурсов.

## Проверка и перенос

1. Зафиксировать реально работающий публичный UI/исходник и обслуживающий Compose
   release. Не брать текущий checkout целиком: там неопубликованные UI-изменения.
   У Oracle записано несовпадение serving release и `current`; не считать симлинк
   достоверной версией. Старую финализацию автоматически не запускать.
2. Проверить подписку Azure, spending limit, остаток кредита и доступные размеры.
   Для UAE North и West Europe использовать только доступные регионы; выбрать
   по задержке, скорости загрузки из Узбекистана/СНГ и полной стоимости. Сначала
   изолированная база и preview; создание ресурсов не выполнено этим исследованием.
3. Проверить Chrome/Edge: чистый первый вход по URL, API недоступен, медленная
   сеть, скачивание/прерывание/дозагрузка всего набора; затем полностью закрыть
   браузер, отключить сеть, открыть URL/PWA, пройти полёт на каждой карте,
   урок/задание, изменения сборки и сохранение/чтение реплея. Проверить удалённый
   файл, отказ persistent storage, нехватку места, старую и новую версии.
4. UI-кнопки/индикаторы офлайна показать рядом с текущим публичным интерфейсом.
   Сохранять существующую компоновку; публикация только после явного допуска на
   выпуск показанного результата. Не включать отвергнутые макеты или иные
   неопубликованные правки попутно с инфраструктурой.
5. Перед переключением остановить новые записи/заезды старого backend, дождаться
   завершения, получить свежую согласованную производственную копию, восстановить
   на Azure и сверить все исходные строки. Перенести секретные env по защищённому
   каналу, не из локальной базы разработчика. Проверить аккаунт, флот, прогресс,
   две реальные сессии и 20 клиентов на отдельной нагрузочной базе.
6. Переключать публичный адрес только после HTTPS/API/WSS/Range/cache и браузерных
   проверок из внешней сети. Иметь рабочий Azure hostname, не зависящий от DuckDNS;
   домен/новый origin определить до подготовки офлайн-кэша. При откате после новых
   записей переносить актуальную БД обратно, не включать старую устаревшую копию.
7. Проверять отдельно доступность страницы, API и небольшой ресурс, сохранять
   времена/DNS/TLS/коды ошибок для будущих сбоев. Мониторинг и уведомления
   подготовить без платных сервисов; расписание в этом исследовании не создано.
   После приёмки вывести Oracle из обслуживания, сохранив проверяемые резервные
   копии и путь восстановления. Ничего автоматически не удалять.

Эти работы улучшат независимость и доступность запуска, но не доказывают
60 FPS на UHD 620 и не устраняют все паузы обработки/отрисовки больших карт.
