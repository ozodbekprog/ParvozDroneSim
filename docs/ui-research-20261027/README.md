# PARVOZ: исследование UI и материалы для выбора

27 октября 2026, Asia/Tashkent. Статус: **обсуждение, дизайн не выбран**.

**28 октября:** пользователь отклонил все три сгенерированных концепта и
потребовал реальный актуальный кадр ангара в качестве общего фона. Новые
HTML-варианты и проверка неизменности кадра —
[в следующем пакете](../ui-research-20261028/README.md). Отклонённые изображения
ниже сохранены только как история исследования.

Пользователь задал новый порядок: исследование и визуальное обсуждение → план →
реализация только после одобрения. Этот документ не утверждает палитру, новый
логотип, компоновку или миграцию UI. Код игры, её зависимости и Oracle в рамках
этого этапа не меняются. Начальная ревизия: `6d909e7dac121b998305438c81ada70557611ad4`,
ветка `codex/demand-pilots`. Незавершённые материалы презентации другого чата
исключены из изменений этого этапа.

## Вывод исследования

Причина повторных неудачных переделок шире отсутствия библиотеки: нет одного
принятого визуального образца и контракта компонентов, а общие CSS-файлы
последовательно переопределяют друг друга. Ещё один набор классов поверх них
сохранит эту проблему. Готовая библиотека полезна для поведения: фокус, клавиатура,
диалоги, выбор, числовые поля. Композицию, количество данных и фирменный образ
нужно выбирать отдельно с пользователем.

Два кандидата заслуживают следующей практической проверки: **Web Awesome Core**
для текущего DOM-стека и **Base UI либо React Aria** для выделенного React-слоя.
Это технический shortlist, не решение о внедрении. React не установлен в игре;
его добавление ради внешнего вида кнопок само по себе не обосновано.

## 1. Публичная проверка

Проверен именно [публичный сайт](https://parvoz-drone-sim.duckdns.org/), Chrome,
а не локальный Vite. Публичный entry: `/assets/index-OPei9JC_.js`, CSS:
`/assets/index-DRMy7-Vl.css`. Последние локальные исправления Workbench и справочник
из `6d909e7` не следует считать опубликованными.

Для первого прохода удалены только CacheStorage этого origin:
`parvoz-downloaded-assets-v1` и `parvoz-encoded-assets-v1`. Для вкладки включены
`Network.setCacheDisabled` и `Network.setBypassServiceWorker`, затем выполнена
перезагрузка. Получены ненулевые сетевые передачи: entry JS — 801140 байт
transfer / 800840 encoded body, CSS — 34787 / 34487. Это сетевые размеры данного
ответа, не распакованный JS и не стоимость новой UI-библиотеки. Cookies,
localStorage, IndexedDB с повторами и кэши других сайтов не очищались.
Метод соответствует отдельному учёту [HTTP-кэша](https://developer.chrome.com/docs/devtools/network/reference)
и [обхода service worker](https://chromedevtools.github.io/devtools-protocol/tot/Network/).

Первый проход: CSS viewport 1920×869, DPR 1. Затем измерен CSS viewport
1280×720, DPR ≈0.8: исходный zoom Chrome 80% потребовал override 1024×576.
Размер PNG не равен автоматически CSS viewport. Качество Ultra не менялось;
это проверка UI, не приёмка FPS на UHD 620. Chrome временно отключился при
обновлении доступных плагинов; сохранённые снимки от этого не стали локальной
версией. Повторный проход описан в `browser-verification.md`.

### Конкретные предложения для обсуждения

`After` ниже означает предлагаемый результат, **не выполненную правку**.

| Before | After | Why |
| --- | --- | --- |
| Много вложенных рамок и одинаковых заголовков у вторичных групп; Tuning рассыпан по краям сцены | Одна рабочая поверхность; связанные поля рядом, разделение отступами и тонкими линиями; модель остаётся контекстом | Уменьшает число визуальных конкурентов, сохраняет функциональность |
| Характеристики в отдельном модальном окне | Краткое сравнение рядом с выбираемой деталью, полный набор раскрывается отдельно | Игрок видит причинную связь без переключения окна |
| Масса, энергия и отклик выглядят просто крупными числами | Подписанные шкалы с единицами, числом и прошлым значением; только затронутые изменения акцентированы | Шкала даёт сравнение, число даёт точность |
| Параметры, которые нельзя регулировать напрямую, выглядят как потенциальные ползунки | Для рассчитанных характеристик read-only meter; для реально изменяемого параметра slider + точное поле | У элемента понятное поведение, меньше ложных ожиданий |
| Универсальное «меньше масса — лучше, больше сопротивление — хуже» | До согласования нейтральные знаки и маркеры; семантика зелёного/красного определяется отдельно | Пользователь уже отверг автоматическую трактовку цели настройки |
| Смена категории Settings меняет геометрию оболочки | Один стабильный контейнер и положение навигации, меняется только содержимое | Сохраняет ориентиры и положение фокуса |
| Числовые таблицы с ломаными подписями | Явные строки Roll / Pitch / Yaw с переводом в пояснении, выровненные числа; Rates и PID читаются независимо | Технические термины узнаваемы, локализация не ломает сетку |
| Внешне одинаковые обычные и рискованные действия | Один основной следующий шаг; Import/Export и удаление — в явно подписанных вторичных действиях | Снижает случайные действия и перегруз |
| Добавление очередного глобального stylesheet | Контракт состояний и токенов, затем замена одного компонента целиком | Исправление становится устойчивым, а не новым override |

Что подтверждено кодом: в `src/main.js:8`–`25` подключено 17 локальных CSS-файлов;
`src/game-ui.css:190`, `src/interface-polish.css:15` и `src/compact-ui.css:22`
затрагивают одни и те же поверхности; `src/compact-ui.css:10` переопределяет
семейство шрифта уже импортированных DM Sans/Barlow. Это свидетельство нескольких
слоёв оформления, но не доказательство конкретной причины каждого публичного
бага: исходники локально уже новее опубликованной сборки.

### Доступность: что ещё требует практической проверки

По screenshot видны риски мелких/ломаных подписей и слабого различия состояний.
Accessibility tree подтверждает доступные имена многих контролов, но кнопки
категорий объявляются pressed-controls, а не полноценными tabs. Это не делает
их автоматически невалидными; если ожидается tab interaction, нужен полный
контракт стрелок/Tab/ARIA. Снимок не подтверждает контраст, чтение NVDA,
клавиатурный focus trap, gamepad-навигацию и отсутствие конфликта Esc с полётом.
Нельзя обещать WCAG-compliance только после подключения библиотеки.

Без production build выбранного набора нельзя честно назвать стоимость в KB,
утверждать улучшение FPS или ранжировать варианты по производительности.

### Что важно именно игре, а не обычному сайту

Основной 3D renderer и цикл симуляции должны остаться независимыми от меню.
Ни один выбранный набор не должен получать setState/DOM-update каждый кадр без
нужды. Открытие панели должно согласовываться с pointer lock, Esc, блокировкой
flight hotkeys в input и возвратом фокуса. Повторный вход не должен пересоздавать
все thumbnails или 3D-сцены. Custom elements требуют cleanup при удалении;
React-root требует явного unmount. Эти риски важнее популярности пакета.

Нативные [dialog](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog),
input/range/select — допустимые платформенные готовые компоненты для простых
задач. Их не нужно заменять усложнёнными самодельными аналогами. Но нативный
диалог не выбирает композицию, не переводит игру и не интегрирует gamepad сам.

### Условия практического сравнения после выбора направления

Это критерии принятия решения, не утверждённый план реализации: сравнить один
и тот же набор Button / Dialog / Tabs / NumberField / Slider / read-only Meter /
Select / Switch с RU/UZ/EN. Проверить keyboard, restore focus, Esc и pointer lock;
720p и широкое окно; длинные подписи; повторные mount/unmount; cold transfer,
gzip/Brotli JS+CSS, parse/evaluate, long tasks и retained heap. Все замеры —
на одинаковых сценариях. До них shortlist остаётся гипотезой. Готовая библиотека
не является самостоятельным лечением геймплейных статтеров.

## 4. Дизайнер, SEO и маркетолог

**Дизайнер.** Одна понятная задача на экран: выбрать полёт, сравнить дрон,
изменить деталь, настроить управление. Нужны три уровня информации: действие и
критический статус; параметры текущего решения; подробности по запросу.
Это не означает спрятать функции или навязать новичку упрощённую физику.
Для Workbench краткая панель должна сохранять связь «что меняю → что меняется».
Какие именно шкалы постоянные и какая плотность удобна, пользователь выбирает
на визуальном примере. Зелёный/красный не утверждены.

**SEO.** У публичного документа наблюдались title, viewport и charset, но не
description, canonical, Open Graph или hreflang. В локальном `index.html:6`
также только title; тело до запуска JS — индикатор подготовки. Значит, хорошая
игровая панель сама по себе не объяснит продукт поиску и предпросмотру ссылки.
Возможное направление для обсуждения: лёгкое индексируемое описание продукта,
понятный «Играть в браузере», управление/требования/языки и реальные screenshots,
выделенный вход в игру. Пользователь пока не заказывал новую landing page:
этот вывод не является разрешением её строить. Canonical важен также для двух
работающих доменов. Реальное состояние индекса Google и Search Console не
проверено, обещаний ранжирования нет.
[Основание: Google Search Central](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics).

**Маркетолог.** Новому игроку нужно за несколько секунд понять, что это за
симулятор и куда ведёт основное действие. Названия Start/Class без пояснения
должны пройти проверку понимания. «Запустить первый полёт», «Настроить пульт»,
«Продолжить» — обсуждаемые формулировки, не согласованный текст. Карты/дроны,
доступные после загрузки, надо отличать от ещё загружаемых; время ожидания и
готовность объяснять честно. Официальный
[Liftoff](https://www.liftoff-game.com/liftoff-fpv-drone-racing) показывает роль
продукта и реальное FPV-оборудование, а
[VelociDrone manual](https://www.velocidrone.com/desktop_manual) разделяет быстрый
старт, выбор модели, сцены и настройки. Это примеры структуры, не разрешение
копировать их бренд/графику и не доказательство, что их UI без недостатков.

Для будущей проверки полезны время до первого успешного полёта, число возвратов
при выборе детали и ошибки навигации. Это метрики исследования, а не уже
подключённая аналитика: сбор поведения игроков и внешние trackers не добавлены.

## 5. Визуальный выбор

В чате показаны три **статических** концепта одного Workbench. Порядок определяется
порядком фактического показа результатов, а не очередью задумок:

1. [Первое показанное изображение](concepts/01.png).
2. [Второе показанное изображение](concepts/02.png).
3. [Третье показанное изображение](concepts/03.png).

Файлы не подключены к игре. Это иллюстрации для сравнения композиции, палитры,
характера кнопок и плотности. Генерация использовала один реальный снимок Parts
как reference. Имена деталей, числа/геометрия шкал, улучшенное освещение и
детализация изображения не являются проверенными данными/графикой текущей игры.
Некоторые концепты меняют написание wordmark или пропускают навигацию: это
**не одобрено** и не должно незаметно попасть в реализацию. Особенно важно:
размеры bars и знаки изменений на картинке не задают физические формулы.

Происхождение, briefs генерации и hash изображений: `ASSETS.md` и
`concepts/briefs.json`. Полные отправленные prompts сохранены в вызовах Image Gen
этого чата. Снимки публичного Liftoff-контента остаются только
материалом согласованного тестового исследования в приватном репозитории,
не новым подтверждением прав распространения.

Следующий шаг — выбор или корректировка пользователем визуального направления,
палитры, плотности и правила сравнения. Затем готовится отдельный план для
одобрения. Выбор изображения сам по себе не отменяет требование пользователя
одобрить план до изменения игры.
