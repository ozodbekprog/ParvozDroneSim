# Developer content workflow

**The folder workflow is now primary.** Use [asset folders, export and delivery](ASSET-WORKFLOW.md) to drop GLBs into `content/` or edit in Blender/Unity. The guide below describes the optional local editor. Its generated catalog and delivery assets are output; the editable source definitions live in `content/`. Publishing writes those source packages, and development changes are compiled automatically. Actual models export at **http://127.0.0.1:2570/editor/export.html**. GLB uploads now allow up to 250 MB.

Start the game with `npm start` or `Play.cmd`. On the same PC open **http://127.0.0.1:2570/editor/**. The editor binds to loopback and does not appear in the player menu. Published data lives in [catalog.json](../public/content/catalog.json), assets in [assets](../public/content/assets/), and the original generated scenery/aircraft recipes in [recipes.js](../public/content/recipes.js). The game and server read the same catalog. Editing these files directly is also supported. Keep stable IDs if you want old builds, records and replays to keep referring to the same content.

The editor opens with every built-in map, aircraft, part, mission and tutorial in its list. Select an entry and edit its fields or choose **+ Add Item**. For a map, choose a course, drag the start marker and gates with W/E/R, and use the up arrows to set checkpoint order. Each course has its own laps and start position. Challenges refer to a map and course; tutorials also carry ordered instruction steps. Use the **Full item data** section for optional fields not exposed individually. The editor saves an independent draft first. **Publish** validates the entire catalog, copies the previous catalog to `catalog.json.bak`, and replaces it atomically. Run `npm run content:check`, rebuild, and restart the server to load the published version.

## Models, materials and collision

- **GLB** is the runtime format. The editor accepts `.glb`, `.fbx`, and `.obj`. FBX and OBJ are converted to GLB in the local editor before upload. They should be self-contained; separate OBJ `.mtl` files and detached texture paths are not imported automatically. Upload textures separately as material overrides. Model coordinates are meters, Y up, +Z forward. Imported files are stored under `public/content/assets/` and served to players by the game server.
- A map can have a main model and scene objects. Missions and tutorials can add their own scene objects. Select an object to move, rotate, scale, replace its model or edit named mesh materials. Built-in procedural maps use the same catalog fields and material overrides as imported maps. Adding a main GLB replaces that map's procedural scenery, while the existing course and collision entries remain editable.
- Visible triangles do **not** automatically become collision. For static maps, objects, lessons and missions, choose **Generate triangle collision** to bake a static triangle proxy, or place and size simpler boxes. A simplified collision model improves performance. Each map, mission or tutorial stores collision with its own content entry. Collision generation has a 100,000-triangle limit per entry; simplify large source models first.
- Drones use a compound set of spheres for their body and motors, rather than a single square box. Select a drone and use **Fit spheres to model**, then inspect and adjust the spheres in the 3D viewport. This is an approximation of the shape, designed for real-time physics; detailed per-triangle collisions on a moving quad are too costly and unstable. Parts may replace built-in visible pieces without replacing the whole drone. Their mass/thrust/drag values and material overrides live with the part data.
- Newly authored parts default to zero credits. Set `cost` in the item data to sell one through the hangar. New drones default to starter access; an `unlock` value can require career progress. Existing IDs remain available after publication.

Players can edit the published folders manually in their own copy of the project, then rebuild. No player-facing import or publish control is present.

The same catalog can be exported with `npm run content:export` for a future Unity project. GLB assets and content IDs are reusable, but Unity needs its own rendering, editor integration and C# flight implementation.
